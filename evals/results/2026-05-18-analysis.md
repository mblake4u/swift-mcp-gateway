## Failure analysis — five clusters

I pulled all 30 individual failures across both eval runs (30 total, 18 unique × multiple models), plus one finding from the axis-3 probe. They sort into five distinct clusters, only one of which is "the model is bad."

### Cluster 1 — Partial send specifications (test-set bug)

**Cases affected:** `ts-011`, `ts-015`, `ts-016`, `ts-017`
**Models that failed:** all six runs failed all four cases on the send-tool axis.

**Pattern.** The test set asks the model to send a message with no payload provided. Example:
> "Send an MT103 from CITIUS33 to BARCGB22 — payload below" (but no payload follows)

**Every model refused to call the tool and asked for clarification.** This is **correct real-world behaviour** — inventing an MT103 payload from thin air would be a catastrophic agent failure. The test set's "expected_tool: send_fin_message" assumption is wrong; the right gold-standard answer for these cases is "no tool / ask clarification" (i.e. axis = negative).

**Verdict.** Test-set bug, not a model failure. **Strips 4 cases × 6 model runs = 24 false-negatives from the headline numbers.** Adjusted figures:

| Run | Adjusted overall (excluding partial-send cases) |
|---|---|
| `opus-4-7` | 26/26 = **100%** |
| `sonnet-4-6` | 21/26 = 81% (still has the 2 negative failures) |
| `haiku-4-5` (Run A) | 19/26 = 73% (additional cluster-2 and cluster-3 failures) |
| `opus-4-5` | 24/26 = 92% (cluster-2 failures only) |
| `sonnet-4-5` | 24/26 = 92% |
| `haiku-4-5` (Run B) | 20/26 = 77% |

**v2 test-set action:** rewrite the 4 cases with full payloads provided, OR re-categorise as negatives.

### Cluster 2 — Singular/plural confusion (product naming issue)

**Cases affected:** `ts-008` (`download_fin_messages` plural), `ts-012` (`download_interact_messages` plural)
**Models that failed:** sonnet-4-6, haiku-4-5 (both runs), opus-4-5.

**Pattern.** Multiple models picked the singular `download_fin_message` / `download_interact_message` when the case asked for the plural list endpoint:
> "Fetch the FIN messages for distribution abc-123"

Models map "messages" (plural noun) ambiguously between the two endpoints. Tool descriptions tried to disambiguate but it's a fundamentally fragile API contract.

**Verdict.** Real product finding, not a model failure. The naming convention `download_X_messages` vs `download_X_message` is **one-character-different and semantically distinct** — a design smell.

**Product fix (out of scope for closeout, captured as backlog):** rename to follow a consistent verb pattern. Best practice for tool naming is verb-led, with explicit cardinality:
- `list_fin_messages` (plural, returns array)
- `get_fin_message` (singular, returns one)

This mirrors a standard REST convention. The CRUD verb communicates cardinality unambiguously.

### Cluster 3 — Jargon mapping fails on small models

**Cases affected:** `ts-013` ("What MX messages do we have queued?")
**Models that failed:** `haiku-4-5` only — both runs.

**Pattern.** Haiku mapped "MX messages" → `list_distributions` rather than → `download_interact_messages`. The MX-format jargon (industry shorthand for InterAct, the MX-message-type service) was not bridged.

Both Sonnet and Opus tiers handled the mapping correctly. The 4.5 → 4.6 / 4.7 generation jump at Sonnet/Opus tier did not change this — it's a small-model precision issue, not a generation issue.

**Verdict.** Genuine model-tier finding. Worth reporting: **small models lose precision on industry jargon even when the larger models in the same family handle it cleanly.**

**Product mitigation:** enrich `download_interact_messages` description to explicitly mention "MX" as a synonym. Tool-description engineering is a partial fix.

### Cluster 4 — Substitution despite system-prompt refusal instruction

**Cases affected:** `neg-003` ("Cancel distribution abc-123"), `neg-004` ("Search messages from yesterday")
**Models that failed:** sonnet-4-6 (both negatives), sonnet-4-5 (neg-003 only).

**Pattern.** Two cases where no appropriate tool exists, but the model substituted a near-match anyway:
- `neg-003`: cancel → `nak_distribution` (cancel ≈ reject semantically, but conceptually different)
- `neg-004`: search by date → `list_distributions` (no date filter, but model called it anyway)

This is despite an explicit system-prompt instruction:
> "Do not invent capabilities. Do not silently substitute a similar tool for one that doesn't exist."

**Verdict.** Genuine model behaviour finding. **System-prompt refusal instructions are not perfectly followed**, particularly under semantic-similarity pull.

Interestingly:
- **Opus 4-7 and Haiku 4-5 followed the instruction**. Both got 6/6 on negatives.
- **Sonnet (both 4-5 and 4-6) is the substitution-prone tier.** This is a surprising tier-specific finding that warrants further investigation.

**Mitigation options for future hardening:**
1. Strengthen the system prompt with explicit example refusals.
2. Add a meta-tool `report_unsupported_request(reason)` that gives the model an explicit refusal pathway — refusing-by-action is often better than refusing-by-inaction.
3. Post-process tool calls against a per-tool allow-list of intent matches.

### Cluster 5 — Tool/API contract mismatch (probe-found bug, FIXED)

**Surfaced by:** axis-3 probe v1 (`2026-05-18-115953-probe`). Not caught by axes 1+2 — the eval test cases all included a distribution_id where needed, so the model never triggered the bug.

**Pattern.** Two tools declared `distribution_id` as **optional**:

```python
def download_fin_messages(distribution_id: str | None = None) -> dict:
    """Download one or several FIN messages ready for distribution."""
```

But the underlying Swift API requires `distribution-id` as a query parameter and returns HTTP 400 (`SwAP504 — Query parameter 'distribution-id' is required`) without it. Net effect: an agent calling either tool without args (e.g. "Show me the FIN messages") gets a confusing 400 with no actionable diagnostic.

**Verdict.** Real product bug. The tool surface lied about its preconditions. **Fixed in gateway v0.1.1-dev** — `distribution_id` made required in both `download_fin_messages` and `download_interact_messages`, with the docstring explicitly naming the Swift-API constraint. `tool_schemas.json` updated to match.

**Methodology takeaway.** Operational probing catches contract-mismatch bugs that pure model evaluation misses. The axes are genuinely orthogonal — neither subsumes the other.

**Cross-finding interaction with Cluster 2.** After the fix, the singular/plural naming confusion (Cluster 2) gets sharper — both tools now share the same required arg shape, making the singular-vs-plural distinction even more arbitrary. Reinforces the v2 backlog rename recommendation (`list_*` / `get_*`).

## Cross-cutting observations

### Latency

| Model | Mean tool-selection latency | Notes |
|---|---|---|
| `haiku-4-5` | ~1,500 ms | Roughly 2× faster than Sonnet/Opus on the same task. |
| `sonnet-4-6` / `opus-4-7` | ~3,200–3,600 ms | Similar latencies; the tier difference is in quality not speed at this task size. |

Negative-case latency is consistently the highest (3,000–5,700 ms). The model "thinks harder" before declining to call a tool. This is a real finding for agent UX design — **refusal is expensive on the latency axis.**

### Non-determinism

`haiku-4-5-20251001` appeared in both runs (same pinned snapshot, same system prompt, same test set) and produced **slightly different results**: 11/18 vs 12/18 on tool selection. Default temperature is non-zero; one-off variance accounts for the 1-case swing.

**Methodology implication:** for production benchmark publication, future eval runs should either set `temperature=0` or run each case N times and report mean+stddev. v1 results here are single-shot at default temperature, documented as a known limitation.

### Generation comparison (Run A vs Run B at the Opus tier)

| Model | Tool-selection pass rate | Failures distinct from cluster-1 |
|---|---|---|
| `opus-4-5-20251101` | 67% | 2 (cluster 2) |
| `opus-4-7` | 78% | 0 |

After stripping the test-set bug (cluster 1), **opus-4-7 went from 92% → 100% over opus-4-5 on the cluster-2 cases** (singular/plural disambiguation). A material capability improvement on the same task surface.

## What this run is good for

✅ **Establishing a baseline.** First measurement. Future runs can compare.
✅ **Validating the methodology.** All three axes produced signal; cluster framing is actionable.
✅ **Surfacing test-set bugs.** Cluster 1 is the kind of issue you only find by running the test.
✅ **Surfacing product issues.** Cluster 2 names a real naming-convention problem.
✅ **Surfacing tier-specific findings.** Cluster 3 (small-model jargon) and Cluster 4 (Sonnet substitution) are nontrivial.

## What this run is NOT good for

❌ Treating the 87% headline as a final number. Cluster 1 contaminates it.
❌ Recommending a model based on these results alone. 30 cases is a baseline, not a verdict.
❌ Inferring SLA-grade latency. Single-region, single-time-of-day, sandbox.
